Le projet Go accueille tous les contributeurs.

Ce document est un guide pour t'aider à traverser le processus de contribution au projet Go, qui diffère quelque peu de celui utilisé par d'autres projets open source. Nous partons du principe que tu as une compréhension de base de Git et de Go.

En plus des informations présentes ici, la communauté Go maintient une page wiki CodeReview. N'hésite pas à contribuer à ce wiki au fur et à mesure que tu apprends le processus de review.

Note que le front end gccgo est hébergé ailleurs ; voir Contribuer à gccgo.

Devenir contributeur

Vue d'ensemble

La première étape consiste à s'enregistrer comme contributeur Go et à configurer ton environnement. Voici une liste des étapes requises à suivre :

  • Étape 0 : Choisis un seul compte Google que tu utiliseras pour contribuer à Go. Utilise ce compte pour toutes les étapes suivantes et assure-toi que git est configuré pour créer des commits avec l'adresse e-mail de ce compte.
  • Étape 1 : Signe et soumet un CLA (Contributor License Agreement).
  • Étape 2 : Configure les identifiants d'authentification pour le dépôt Git de Go. Visite go.googlesource.com, clique sur "Generate Password" dans le menu en haut à droite de la page, et suis les instructions.
  • Étape 3 : Enregistre-toi sur Gerrit, l'outil de code review utilisé par l'équipe Go, en visitant cette page. Le CLA et l'enregistrement ne doivent être effectués qu'une seule fois pour ton compte.
  • Étape 4 : Installe git-codereview en exécutant go install golang.org/x/review/git-codereview@latest

Si tu préfères, il existe un outil automatisé qui te guide à travers ces étapes. Il suffit d'exécuter : 

$ go install golang.org/x/tools/cmd/go-contrib-init@latest
$ cd /code/to/edit
$ go-contrib-init

La suite de ce chapitre développe ces instructions. Si tu as terminé les étapes ci-dessus (manuellement ou via l'outil), saute à la section Avant de contribuer du code.

Étape 0 : Choisir un compte Google

Une contribution à Go est faite via un compte Google avec une adresse e-mail spécifique. Assure-toi d'utiliser le même compte tout au long du processus et pour toutes tes contributions ultérieures. Tu devras peut-être décider d'utiliser une adresse personnelle ou professionnelle. Ce choix dépend de qui détiendra les droits d'auteur sur le code que tu vas écrire et soumettre. Tu pourrais vouloir en discuter avec ton employeur avant de décider quel compte utiliser.

Les comptes Google peuvent être des comptes e-mail Gmail, des comptes d'organisation G Suite, ou des comptes associés à une adresse e-mail externe. Par exemple, si tu as besoin d'utiliser une adresse e-mail d'entreprise existante non gérée via G Suite, tu peux créer un compte associé à ton adresse e-mail existante.

Tu dois aussi t'assurer que ton outil Git est configuré pour créer des commits avec l'adresse e-mail choisie. Tu peux configurer Git de façon globale (par défaut pour tous les projets), ou localement (pour un projet spécifique). Tu peux vérifier la configuration actuelle avec cette commande : 

$ git config --global user.email  # check current global config
$ git config user.email           # check current local config

Pour changer l'adresse configurée : 

$ git config --global user.email name@example.com   # change global config
$ git config user.email name@example.com            # change local config

Étape 1 : Contributor License Agreement

Avant d'envoyer ton premier changement au projet Go, tu dois avoir signé l'un des deux CLA suivants. Le CLA à signer dépend de qui détient les droits d'auteur sur ton travail.

  • Si tu es le titulaire des droits d'auteur, tu devras accepter le contributor license agreement individuel, qui peut être complété en ligne.
  • Si ton organisation est titulaire des droits d'auteur, l'organisation devra accepter le contributor license agreement d'entreprise.

Tu peux vérifier les accords actuellement signés et en signer de nouveaux sur le site Google Developers Contributor License Agreements. Si le titulaire des droits d'auteur pour ta contribution a déjà signé l'accord dans le cadre d'un autre projet open source Google, il n'est pas nécessaire de le signer à nouveau.

Si le titulaire des droits d'auteur pour le code que tu soumets change—par exemple, si tu commences à contribuer du code au nom d'une nouvelle entreprise—envoie un e-mail à la golang-dev mailing list. Cela nous permettra de connaître la situation afin de nous assurer qu'un accord approprié est signé.

Étape 2 : Configurer l'authentification git

Le dépôt principal de Go se trouve sur go.googlesource.com, un serveur Git hébergé par Google. L'authentification sur le serveur web se fait via ton compte Google, mais tu dois aussi configurer git sur ton ordinateur pour y accéder. Suis ces étapes :

  1. Visite go.googlesource.com et clique sur "Generate Password" dans le menu en haut à droite de la page. Tu seras redirigé vers accounts.google.com pour te connecter.
  2. Après t'être connecté, tu seras conduit sur une page intitulée "Configure Git". Cette page contient un script personnalisé qui, exécuté localement, configurera Git pour conserver ta clé d'authentification unique. Cette clé est associée à une autre générée et stockée sur le serveur, de façon analogue au fonctionnement des clés SSH.
  3. Copie et exécute ce script localement dans ton terminal pour stocker ton jeton d'authentification secret dans un fichier .gitcookies. Si tu utilises un ordinateur Windows et exécutes cmd, tu dois plutôt suivre les instructions dans le bandeau jaune pour exécuter la commande ; sinon exécute le script normal.

Étape 3 : Créer un compte Gerrit

Gerrit est un outil open source utilisé par les mainteneurs Go pour discuter et passer en review les soumissions de code.

Pour enregistrer ton compte, visite go-review.googlesource.com/login/ et connecte-toi une fois avec le même compte Google que tu as utilisé ci-dessus.

Étape 4 : Installer la commande git-codereview

Les changements apportés à Go doivent être passés en review avant d'être acceptés, peu importe qui fait le changement. Une commande git personnalisée appelée git-codereview simplifie l'envoi de changements à Gerrit.

Installe la commande git-codereview en exécutant : 

$ go install golang.org/x/review/git-codereview@latest

Assure-toi que git-codereview est installé dans le PATH de ton shell, afin que la commande git puisse le trouver. Vérifie que 

$ git codereview help

affiche le texte d'aide, et non une erreur. Si une erreur s'affiche, assure-toi que $GOPATH/bin est dans ton $PATH.

Sur Windows, avec git-bash, tu dois t'assurer que git-codereview.exe se trouve dans le exec-path de git. Exécute git --exec-path pour trouver le bon emplacement, puis crée un lien symbolique ou copie simplement l'exécutable depuis $GOPATH/bin vers ce répertoire.

Avant de contribuer du code

Le projet accepte les patches de code, mais pour s'assurer que tout est bien coordonné, tu dois discuter de tout changement significatif avant de commencer le travail. Il est recommandé de signaler ton intention de contribuer dans le suivi des problèmes, soit en ouvrant un nouveau problème, soit en te déclarant sur un problème existant.

Où contribuer

Le projet Go se compose du dépôt principal go, qui contient le code source du langage Go, ainsi que de nombreux dépôts golang.org/x/.... Ceux-ci contiennent les différents outils et infrastructures qui supportent Go. Par exemple, golang.org/x/pkgsite est pour pkg.go.dev, golang.org/x/playground est pour le Go playground, et golang.org/x/tools contient une variété d'outils Go, dont le serveur de langage Go, gopls. Tu peux voir la liste de tous les dépôts golang.org/x/... sur go.googlesource.com.

Consulter le suivi des problèmes

Que tu saches déjà quelle contribution apporter ou que tu cherches une idée, le suivi des problèmes est toujours le premier endroit où aller. Les problèmes sont triés pour les catégoriser et gérer le flux de travail.

La majorité des dépôts golang.org/x/... utilisent également le suivi des problèmes principal de Go. Cependant, quelques-uns de ces dépôts gèrent leurs problèmes séparément, alors assure-toi de consulter le bon suivi pour le dépôt auquel tu souhaites contribuer.

La plupart des problèmes seront marqués avec l'un des labels de workflow suivants :

  • NeedsInvestigation : Le problème n'est pas pleinement compris et nécessite une analyse pour en comprendre la cause racine.
  • NeedsDecision : le problème est relativement bien compris, mais l'équipe Go n'a pas encore décidé de la meilleure façon de le résoudre. Il vaut mieux attendre une décision avant d'écrire du code. Si tu souhaites travailler sur un problème dans cet état, n'hésite pas à "relancer" les mainteneurs dans les commentaires du problème si du temps s'est écoulé sans décision.
  • NeedsFix : le problème est pleinement compris et du code peut être écrit pour le corriger.

Tu peux utiliser la fonctionnalité de recherche de GitHub pour trouver des problèmes sur lesquels aider. Exemples :

  • Problèmes nécessitant une investigation : is:issue is:open label:NeedsInvestigation
  • Problèmes nécessitant une correction : is:issue is:open label:NeedsFix
  • Problèmes nécessitant une correction avec un changement suggéré : is:issue is:open label:NeedsFix ("golang.org/cl" OR "go.dev/cl")
  • Problèmes nécessitant une correction sans changement suggéré : is:issue is:open label:NeedsFix NOT "golang.org/cl" NOT "go.dev/cl"

Ouvrir un problème pour tout nouveau sujet

À l'exception des changements très mineurs, toutes les contributions doivent être liées à un problème existant. N'hésite pas à en ouvrir un et à discuter de tes plans. Ce processus donne à chacun l'occasion de valider la conception, aide à éviter la duplication des efforts, et garantit que l'idée s'inscrit dans les objectifs du langage et des outils. Il permet aussi de vérifier que la conception est solide avant d'écrire du code ; l'outil de code review n'est pas l'endroit pour les discussions de haut niveau.

Lorsque tu planifies ton travail, note que le projet Go suit un cycle de développement de six mois pour le dépôt principal de Go. La seconde moitié de chaque cycle est un gel de fonctionnalités de trois mois durant lequel seuls les corrections de bugs et les mises à jour de documentation sont acceptées. Les nouvelles contributions peuvent être envoyées durant un gel de fonctionnalités, mais elles ne seront pas mergées avant la fin du gel. Le gel s'applique à l'ensemble du dépôt principal ainsi qu'au code des dépôts golang.org/x/... nécessaire pour compiler les binaires inclus dans la version. Consulte les listes des packages vendorisés dans la bibliothèque standard et la commande go.

Les changements significatifs au langage, aux bibliothèques ou aux outils (ce qui inclut les changements d'API dans le dépôt principal et tous les dépôts golang.org/x, ainsi que les changements de ligne de commande de la commande go) doivent passer par le processus de proposition de changement avant de pouvoir être acceptés.

Les problèmes sensibles liés à la sécurité (uniquement !) doivent être signalés à security@golang.org.

Envoyer un changement via GitHub

Les contributeurs qui participent pour la première fois et sont déjà familiers avec le flux GitHub sont encouragés à utiliser le même processus pour les contributions Go. Bien que les mainteneurs Go utilisent Gerrit pour le code review, un bot appelé Gopherbot a été créé pour synchroniser les pull requests GitHub avec Gerrit.

Ouvre une pull request GitHub comme tu le ferais normalement. Gopherbot créera une change list Gerrit correspondante (un "CL") et publiera un lien vers celle-ci sur ta pull request GitHub ; les mises à jour de la pull request seront également reflétées dans le CL Gerrit. Quand quelqu'un commente le CL, son commentaire sera aussi publié dans ta pull request, tu recevras donc une notification.

Quelques points à garder en tête :

  • Tu auras besoin d'un compte Gerrit pour répondre à tes reviewers, notamment pour marquer les retours comme "Done" si tu les as implémentés comme suggéré. C'est une bonne idée de se familiariser avec Gerrit, par exemple en parcourant les CLs ouverts, en s'abonnant aux mises à jour sur des CLs intéressants (via l'icône étoile), ou en passant en review ou en donnant un +1 aux CLs des autres.
  • Pour mettre à jour la pull request avec du nouveau code, pousse-le simplement sur la branch ; tu peux soit ajouter d'autres commits, soit rebaser et forcer le push (les deux styles sont acceptés).
  • Si la demande est acceptée, tous les commits seront squashés, et la description finale du commit sera composée en concaténant le titre et la description de la pull request. Les descriptions des commits individuels seront ignorées. Voir Écrire de bons messages de commit pour quelques suggestions.
  • Voir la FAQ pour plus de détails.

Envoyer un changement via Gerrit

Il n'est pas possible de synchroniser complètement Gerrit et GitHub, du moins pour l'instant, donc nous recommandons d'apprendre Gerrit. C'est différent mais puissant, et le maîtriser t'aidera à comprendre le flux de travail.

Les sections suivantes donnent un bref aperçu de la soumission d'un changement via Gerrit. Pour plus de détails sur l'interaction avec Gerrit, consulte la documentation de Gerrit. En particulier, nous recommandons de lire les pages Review UI Overview et Basic Gerrit Walkthrough — For GitHub Users.

Vue d'ensemble

Voici une vue d'ensemble du processus global :

  • Étape 1 : Clone le code source depuis go.googlesource.com et assure-toi qu'il est stable en le compilant et en le testant une fois.

    Si tu modifies le dépôt Go principal :

    $ git clone https://go.googlesource.com/go
$ cd go/src
$ ./all.bash                                # compile and test

    Si tu modifies l'un des dépôts golang.org/x/... (golang.org/x/tools, dans cet exemple) : 

    $ git clone https://go.googlesource.com/tools
$ cd tools
$ go test ./...                             # compile and test
  • Étape 2 : Prépare les changements dans une nouvelle branch, créée depuis la branch master. Pour commiter les changements, utilise git codereview change ; cela créera ou amendera un seul commit dans la branch. 
    $ git checkout -b mybranch
$ [edit files...]
$ git add [files...]
$ git codereview change   # create commit in the branch
$ [edit again...]
$ git add [files...]
$ git codereview change   # amend the existing commit with new changes
$ [etc.]
  • Étape 3 : Teste tes changements, soit en exécutant les tests du package que tu as modifié, soit en relançant all.bash.

    Dans le dépôt Go principal :

    $ ./all.bash    # recompile and test

    Dans un dépôt golang.org/x/... :

    $ go test ./... # recompile and test
  • Étape 4 : Envoie les changements pour review à Gerrit en utilisant git codereview mail (qui n'utilise pas l'e-mail, malgré le nom). 
    $ git codereview mail     # send changes to Gerrit
  • Étape 5 : Après une review, applique les changements au même commit unique et envoie-les à nouveau à Gerrit : 
    $ [edit files...]
$ git add [files...]
$ git codereview change   # update same commit
$ git codereview mail     # send to Gerrit again

La suite de cette section décrit ces étapes en détail.

Étape 1 : Cloner le code source

En plus d'une installation récente de Go, tu as besoin d'une copie locale du code source clonée depuis le bon dépôt. Tu peux cloner le dépôt source Go sur ton système de fichiers local où tu veux, tant que c'est en dehors de ton GOPATH (par défaut le répertoire go dans ton répertoire personnel). Clone depuis go.googlesource.com (pas depuis GitHub) :

Dépôt Go principal :

$ git clone https://go.googlesource.com/go
$ cd go

Dépôt golang.org/x/...

(golang.org/x/tools dans cet exemple) : 
$ git clone https://go.googlesource.com/tools
$ cd tools

Étape 2 : Préparer les changements dans une nouvelle branch

Chaque changement Go doit être fait dans une branch séparée, créée depuis la branch master. Tu peux utiliser les commandes git normales pour créer une branch et ajouter des changements à la zone de staging : 

$ git checkout -b mybranch
$ [edit files...]
$ git add [files...]

Pour commiter les changements, utilise git codereview change plutôt que git commit. 

$ git codereview change
(open $EDITOR)

Tu peux modifier la description du commit dans ton éditeur favori comme d'habitude. La commande git codereview change ajoutera automatiquement une ligne Change-Id unique en bas. Cette ligne est utilisée par Gerrit pour faire correspondre les uploads successifs du même changement. Ne la modifie pas et ne la supprime pas. Un Change-Id ressemble à ceci : 

Change-Id: I2fbdbffb3aab626c4b6f56348861b7909e3e8990

L'outil vérifie aussi que tu as exécuté go fmt sur le code source, et que le message de commit suit le format suggéré.

Si tu dois modifier les fichiers à nouveau, tu peux préparer les nouveaux changements et relancer git codereview change : chaque exécution ultérieure amendera le commit existant tout en préservant le Change-Id.

Assure-toi de toujours garder un seul commit dans chaque branch. Si tu ajoutes plus de commits par erreur, tu peux utiliser git rebase pour les squasher ensemble en un seul.

Étape 3 : Tester tes changements

Tu as écrit et testé ton code, mais avant d'envoyer du code pour review, exécute tous les tests pour l'ensemble de l'arbre pour t'assurer que les changements ne cassent pas d'autres packages ou programmes.

Dans le dépôt Go principal

Pour les packages de la bibliothèque standard, tous les tests du package doivent réussir : 

$ go test

La suite de tests courte pour l'ensemble de l'arbre peut être exécutée avec all.bash (sous Windows, utilise all.bat) : 

$ cd go/src
$ ./all.bash

Après avoir tourné pendant un moment et affiché beaucoup de sortie de tests, la commande doit se terminer en affichant : 

ALL TESTS PASSED

Tu peux utiliser make.bash à la place de all.bash pour seulement compiler le compilateur et la bibliothèque standard sans exécuter la suite de tests. Une fois l'outil go compilé, il sera installé sous bin/go dans le répertoire où tu as cloné le dépôt Go, et tu pourras le lancer directement depuis là. Voir aussi la section sur comment tester tes changements rapidement.

Dans les dépôts golang.org/x/...

Exécute les tests pour l'ensemble du dépôt (golang.org/x/tools, dans cet exemple) : 

$ cd tools
$ go test ./...

Si tu t'inquiètes de l'état du build, tu peux consulter le Build Dashboard. Les échecs de tests peuvent aussi être détectés par les TryBots lors du code review.

Certains dépôts, comme golang.org/x/vscode-go, auront des infrastructures de tests différentes, alors vérifie toujours la documentation du dépôt sur lequel tu travailles. Le fichier README à la racine du dépôt contiendra généralement ces informations.

Étape 4 : Envoyer les changements pour review

Une fois le changement prêt et testé sur l'ensemble de l'arbre, envoie-le pour review. Cela se fait avec la sous-commande mail qui, malgré son nom, n'envoie pas directement de mail ; elle envoie simplement le changement à Gerrit : 

$ git codereview mail

Gerrit attribue à ton changement un numéro et une URL, que git codereview mail affichera, par exemple : 

remote: New Changes:
remote:   https://go-review.googlesource.com/99999 math: improved Sin, Cos and Tan precision for very large arguments

Si tu obtiens une erreur à la place, consulte la section Résolution des erreurs mail.

Si ton changement concerne un problème GitHub ouvert et que tu as suivi le format de message de commit suggéré, le problème sera mis à jour dans quelques minutes par un bot, qui liera ton changement Gerrit en commentaire.

Étape 5 : Réviser les changements après une review

Les mainteneurs Go passeront en review ton code sur Gerrit, et tu recevras des notifications par e-mail. Tu peux voir la review sur Gerrit et y laisser des commentaires. Tu peux aussi répondre par e-mail si tu préfères.

Si tu dois réviser ton changement après la review, modifie les fichiers dans la même branch que tu as créée précédemment, ajoute-les à la zone de staging Git, puis amende le commit avec git codereview change : 

$ git codereview change     # amend current commit
(open $EDITOR)
$ git codereview mail       # send new changes to Gerrit

Si tu n'as pas besoin de modifier la description du commit, sauvegarde et quitte simplement l'éditeur. N'oublie pas de ne pas toucher la ligne Change-Id spéciale.

Encore une fois, assure-toi de toujours garder un seul commit dans chaque branch. Si tu ajoutes plus de commits par erreur, tu peux utiliser git rebase pour les squasher ensemble en un seul.

Bons messages de commit

Les messages de commit dans Go suivent un ensemble de conventions spécifiques, dont nous discutons dans cette section.

Voici un exemple de bon message : 

math: improve Sin, Cos and Tan precision for very large arguments

The existing implementation has poor numerical properties for
large arguments, so use the McGillicutty algorithm to improve
accuracy above 1e10.

The algorithm is described at https://wikipedia.org/wiki/McGillicutty_Algorithm

Fixes #159

Première ligne

La première ligne de la description du changement est conventionnellement un court résumé en une ligne du changement, préfixé par le package principal concerné.

Une règle empirique est qu'elle devrait être rédigée de façon à compléter la phrase "This change modifies Go to _____." Cela signifie qu'elle ne commence pas par une majuscule, n'est pas une phrase complète, et résume effectivement le résultat du changement.

Fais suivre la première ligne d'une ligne vide.

Contenu principal

Le reste de la description développe et doit fournir le contexte du changement et expliquer ce qu'il fait. Écris en phrases complètes avec la ponctuation correcte, tout comme pour tes commentaires dans Go. N'utilise pas HTML, Markdown, ou tout autre langage de balisage. Le texte doit être mis à la ligne vers 72 colonnes. Voir Commit messages pour des détails supplémentaires.

Ajoute toute information pertinente, comme les données de benchmark si le changement affecte les performances. L'outil benchstat est utilisé conventionnellement pour formater les données de benchmark dans les descriptions de changement.

Référencer des problèmes

La notation spéciale "Fixes #12345" associe le changement au problème 12345 dans le suivi des problèmes Go. Quand ce changement est finalement appliqué, le suivi des problèmes marquera automatiquement le problème comme résolu.

Si le changement est une étape partielle vers la résolution du problème, écris "Updates #12345" à la place. Cela laissera un commentaire dans le problème renvoyant au changement dans Gerrit, mais ne fermera pas le problème quand le changement est appliqué.

Si tu envoies un changement pour un dépôt golang.org/x/..., tu dois utiliser la syntaxe complète supportée par GitHub pour t'assurer que le changement est lié au problème dans le dépôt principal, et non dans le dépôt x/. La plupart des problèmes sont suivis dans le suivi des problèmes du dépôt principal. La forme correcte est "Fixes golang/go#159".

Le processus de review

Cette section explique le processus de review en détail et comment aborder les reviews après qu'un changement a été envoyé.

Erreurs courantes des débutants

Quand un changement est envoyé à Gerrit, il est généralement trié dans les quelques jours. Un mainteneur y jettera un coup d'oeil et fournira une review initiale qui, pour les contributeurs novices, se concentre généralement sur les aspects cosmétiques de base et les erreurs courantes. Cela inclut des choses comme :

  • Message de commit ne suivant pas le format suggéré.
  • L'absence d'un problème GitHub lié. La grande majorité des changements nécessite un problème lié décrivant le bug ou la fonctionnalité que le changement corrige ou implémente, et un consensus doit avoir été atteint sur le suivi des problèmes avant de procéder. Les reviews Gerrit ne discutent pas du bien-fondé du changement, seulement de son implémentation.
    Seuls les changements mineurs ou cosmétiques seront acceptés sans problème associé.
  • Changement envoyé durant la phase de gel du cycle de développement, quand l'arbre est fermé aux changements généraux. Dans ce cas, un mainteneur pourrait passer en review le code avec une ligne telle que R=go1.12, ce qui signifie qu'il sera revu plus tard quand l'arbre ouvrira pour une nouvelle fenêtre de développement. Tu peux toi-même ajouter R=go1.XX comme commentaire si tu sais que ce n'est pas le bon moment pour le changement.

Trybots

Après une première lecture de ton changement, les mainteneurs déclencheront les trybots, un cluster de serveurs qui exécuteront la suite de tests complète sur plusieurs architectures différentes. La plupart des trybots se terminent en quelques minutes, après quoi un lien sera publié dans Gerrit où tu pourras voir les résultats.

Si l'exécution des trybots échoue, suis le lien et consulte les logs complets des plateformes sur lesquelles les tests ont échoué. Essaie de comprendre ce qui a cassé, mets à jour ton patch pour le corriger, et uploade à nouveau. Les mainteneurs déclencheront une nouvelle exécution des trybots pour voir si le problème a été résolu.

Parfois, l'arbre peut être cassé sur certaines plateformes pendant quelques heures ; si l'échec signalé par le trybot ne semble pas lié à ton patch, va sur le Build Dashboard et vérifie si le même échec apparaît dans d'autres commits récents sur la même plateforme. Dans ce cas, n'hésite pas à écrire un commentaire dans Gerrit pour mentionner que l'échec est sans rapport avec ton changement, afin d'aider les mainteneurs à comprendre la situation. Tu peux aussi chercher dans les problèmes GitHub le message d'erreur qui échoue ou parcourir les problèmes watchflakes récemment mis à jour. Si ton changement est basé sur un commit plus ancien ou s'il semble que quelqu'un d'autre ait déjà résolu le problème, essaie de rebaser sur le dernier commit master via git rebase.

Reviews

La communauté Go accorde beaucoup de valeur aux reviews approfondies. Pense à chaque commentaire de review comme un ticket : tu es censé le "fermer" d'une façon ou d'une autre en agissant dessus, soit en implémentant la suggestion, soit en convainquant le reviewer du contraire.

Après avoir mis à jour le changement, parcours les commentaires de review et assure-toi de répondre à chacun. Tu peux cliquer sur le bouton "Done" pour répondre en indiquant que tu as implémenté la suggestion du reviewer ; sinon, clique sur "Reply" et explique pourquoi tu ne l'as pas fait, ou ce que tu as fait à la place.

Il est tout à fait normal que les changements passent par plusieurs tours de reviews, avec un ou plusieurs reviewers faisant de nouveaux commentaires à chaque fois puis attendant un changement mis à jour avant de reprendre la review. Ce cycle se produit même pour les contributeurs expérimentés, donc ne te décourage pas.

Conventions de vote

À l'approche d'une décision, les reviewers appliqueront un "vote" Code-Review à ton changement. Il y a deux votes possibles :

  • +2 Le changement est approuvé pour être mergé. Seuls les mainteneurs Go (également appelés "approvers") peuvent voter +2.
  • +1 Le changement semble bon, mais soit le reviewer demande des modifications mineures avant de l'approuver, soit il n'est pas un mainteneur et ne peut pas l'approuver, mais souhaite encourager une approbation.

Pour être soumis, un changement doit avoir un Code-Review +2 d'un mainteneur.

Les mainteneurs peuvent aussi appliquer un vote Hold +1 au changement, pour marquer un changement qui ne doit pas être soumis maintenant (par exemple, parce que la review de la proposition pour la nouvelle API dans le changement n'est pas encore terminée).

Pour être soumis, un changement ne doit avoir aucun vote Hold +1 d'un mainteneur.

Enfin, pour être soumis, un changement doit impliquer deux employés de Google, soit comme auteur du changement, soit comme reviewer votant au moins Code-Review +1. Cette exigence est pour des raisons de conformité et de sécurité de la chaîne d'approvisionnement.

Soumettre un changement approuvé

Quand un changement est prêt, un mainteneur le soumettra, ce qui l'ajoute comme commit au dépôt Gerrit.

Les deux étapes (approbation et soumission) sont séparées parce que dans certains cas les mainteneurs peuvent vouloir l'approuver mais pas le soumettre immédiatement (par exemple, l'arbre pourrait être temporairement gelé).

Soumettre un changement l'intègre dans le dépôt. La description du changement inclura un lien vers le code review, qui sera mis à jour avec un lien vers le changement dans le dépôt. Puisque la méthode utilisée pour intégrer les changements est le "Cherry Pick" de Git, les hashes de commit dans le dépôt seront modifiés par l'opération de soumission.

Si ton changement a été approuvé depuis quelques jours sans être soumis, n'hésite pas à écrire un commentaire dans Gerrit pour demander la soumission.

En plus des informations ici, la communauté Go maintient une page wiki CodeReview. N'hésite pas à contribuer à cette page au fur et à mesure que tu en apprends davantage sur le processus de review.

Sujets divers

Cette section rassemble un certain nombre d'autres points qui se situent en dehors du processus problème/modification/code review/soumission lui-même.

Gopls

Lorsque tu travailles sur le dépôt Go principal et que tu utilises gopls avec ton éditeur, la commande go invoquée par gopls doit correspondre à la version du code source sur laquelle tu travailles. La commande go peut être compilée avec make.bash et le répertoire bin doit être ajouté à ton PATH. Voir Gopls : sujets avancés pour des détails supplémentaires.

La documentation complète de Gopls est disponible sur https://go.dev/gopls.

En-têtes de copyright

Les fichiers dans le dépôt Go ne listent pas les noms des auteurs, pour éviter l'encombrement et pour ne pas avoir à maintenir les listes à jour. À la place, ton nom apparaîtra dans le journal des changements.

Les nouveaux fichiers que tu contribues doivent utiliser l'en-tête de copyright standard : 

// Copyright {{now.UTC.Year}} The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

Les fichiers dans le dépôt sont protégés par le droit d'auteur l'année où ils sont ajoutés. Ne mets pas à jour l'année du copyright sur les fichiers que tu modifies.

Résolution des erreurs mail

La façon la plus courante dont la commande git codereview mail échoue est que l'adresse e-mail dans le commit ne correspond pas à celle que tu as utilisée lors du processus d'enregistrement.
Si tu vois quelque chose comme... 

remote: Processing changes: refs: 1, done
remote:
remote: ERROR:  In commit ab13517fa29487dcf8b0d48916c51639426c5ee9
remote: ERROR:  author email address XXXXXXXXXXXXXXXXXXX
remote: ERROR:  does not match your user account.

tu dois configurer Git pour ce dépôt afin d'utiliser l'adresse e-mail avec laquelle tu t'es enregistré. Pour changer l'adresse e-mail et éviter que cela ne se reproduise, exécute : 

$ git config user.email email@address.com

Puis modifie le commit pour utiliser cette adresse e-mail alternative avec cette commande : 

$ git commit --amend --author="Author Name <email@address.com>"

Puis réessaie en exécutant : 

$ git codereview mail

Tester tes changements rapidement

Exécuter all.bash pour chaque modification du code est fastidieux. Même s'il est fortement recommandé de l'exécuter avant d'envoyer un changement, durant le cycle de développement normal tu pourrais vouloir compiler et tester uniquement le package que tu développes.

  • En général, tu peux exécuter make.bash à la place de all.bash pour seulement recompiler la chaîne d'outils Go sans exécuter toute la suite de tests. Ou tu peux exécuter run.bash pour seulement exécuter toute la suite de tests sans recompiler la chaîne d'outils. Tu peux penser à all.bash comme make.bash suivi de run.bash.
  • Dans cette section, nous appellerons le répertoire dans lequel tu as cloné le dépôt Go $GOROOT. L'outil go compilé par $GOROOT/src/make.bash sera installé dans $GOROOT/bin/go et tu pourras l'invoquer directement pour tester ton code. Par exemple, si tu as modifié le compilateur et que tu veux tester comment il affecte la suite de tests de ton propre projet, exécute simplement go test avec lui : 
    $ cd <MYPROJECTDIR>
$ $GOROOT/bin/go test
  • Si tu modifies la bibliothèque standard, tu n'as probablement pas besoin de recompiler le compilateur : tu peux simplement exécuter les tests du package que tu as modifié. Tu peux le faire soit avec la version de Go que tu utilises normalement, soit avec le compilateur Go compilé depuis ton clone (ce qui est parfois nécessaire car le code de la bibliothèque standard que tu modifies peut nécessiter une version plus récente que la version stable que tu as installée). 
    $ cd $GOROOT/src/crypto/sha1
$ [make changes...]
$ $GOROOT/bin/go test .
  • Si tu modifies le compilateur lui-même, tu peux simplement recompiler l'outil compile (qui est le binaire interne invoqué par go build pour compiler chaque package individuel). Après cela, tu voudras le tester en compilant ou en exécutant quelque chose. 
    $ cd $GOROOT/src
$ [make changes...]
$ $GOROOT/bin/go install cmd/compile
$ $GOROOT/bin/go build [something...]   # test the new compiler
$ $GOROOT/bin/go run [something...]     # test the new compiler
$ $GOROOT/bin/go test [something...]    # test the new compiler
    La même chose s'applique aux autres outils internes de la chaîne d'outils Go, comme asm, cover, link, etc. Il suffit de recompiler et d'installer l'outil avec go install cmd/<TOOL> puis d'utiliser le binaire Go compilé pour le tester.
  • En plus des tests standard par package, il y a une suite de tests de haut niveau dans $GOROOT/test qui contient plusieurs tests boîte noire et tests de régression. La suite de tests est exécutée par all.bash mais tu peux aussi l'exécuter manuellement : 
    $ $GOROOT/bin/go test cmd/internal/testdir

Spécifier un reviewer / mettre d'autres personnes en copie

Sauf indication contraire explicite, comme dans la discussion précédant l'envoi du changement, il vaut mieux ne pas spécifier de reviewer. Tous les changements sont automatiquement mis en copie à la golang-codereviews@googlegroups.com mailing list. Si c'est ton tout premier changement, il peut y avoir un délai de modération avant qu'il n'apparaisse sur la mailing list, pour éviter le spam.

Tu peux spécifier un reviewer ou mettre des parties intéressées en copie en utilisant les options -r ou -cc. Les deux acceptent une liste d'adresses e-mail séparées par des virgules : 

$ git codereview mail -r joe@golang.org -cc mabel@example.com,math-nuts@swtch.com

Synchroniser ton client

Pendant que tu travaillais, d'autres ont peut-être soumis des changements au dépôt. Pour mettre à jour ta branch locale, exécute : 

$ git codereview sync

(En coulisses, cela exécute git pull -r.)

Passer en review le code des autres

Dans le cadre du processus de review, les reviewers peuvent proposer des changements directement (dans le flux GitHub, ce serait quelqu'un d'autre attachant des commits à une pull request). Gerrit fournit un accès à des commandes qui t'aideront à importer les changements proposés par un autre développeur afin que tu puisses les passer en review/tester localement. Depuis la page Gerrit du CL que tu veux importer, ouvre le menu "⋮", clique sur le lien "Download patch". Selon ton flux de travail git préféré, choisis la commande appropriée. Les options ressembleront à quelque chose comme ceci : 

$ git fetch https://go.googlesource.com/review refs/changes/21/13245/1 && git checkout FETCH_HEAD

Pour annuler, reviens à la branch sur laquelle tu travaillais.

Configurer des alias git

La commande git-codereview peut être exécutée directement depuis le shell en tapant, par exemple : 

$ git codereview sync

mais il est plus pratique de configurer des alias pour les sous-commandes de git-codereview, afin que ce qui précède devienne : 

$ git sync

Les sous-commandes de git-codereview ont été choisies pour être distinctes de celles de Git, il est donc sûr de définir ces alias. Pour les installer, copie ce texte dans ton fichier de configuration Git (généralement .gitconfig dans ton répertoire personnel) : 

[alias]
	change = codereview change
	gofmt = codereview gofmt
	mail = codereview mail
	pending = codereview pending
	submit = codereview submit
	sync = codereview sync

Envoyer plusieurs changements dépendants

Les utilisateurs avancés peuvent vouloir empiler des commits liés dans une seule branch. Gerrit permet que les changements soient dépendants les uns des autres, formant ainsi une chaîne de dépendances. Chaque changement devra être approuvé et soumis séparément, mais la dépendance sera visible pour les reviewers.

Pour envoyer un groupe de changements dépendants, garde chaque changement comme un commit différent sous la même branch, puis exécute : 

$ git codereview mail HEAD

Assure-toi de spécifier explicitement HEAD, ce qui n'est généralement pas requis lors de l'envoi de changements uniques. Plus de détails peuvent être trouvés dans la documentation git-codereview.
