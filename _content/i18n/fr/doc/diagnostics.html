Introduction

L'écosystème Go fournit un large ensemble d'APIs et d'outils pour diagnostiquer les problèmes de logique et de performance dans les programmes Go. Cette page résume les outils disponibles et aide les utilisateurs Go à choisir le bon pour leur problème spécifique.

Les solutions de diagnostics peuvent être regroupées dans les catégories suivantes :

  • Profiling : Les outils de profiling analysent la complexité et les coûts d'un programme Go tels que son utilisation de la mémoire et les fonctions fréquemment appelées pour identifier les sections coûteuses d'un programme Go.
  • Tracing : Le tracing est un moyen d'instrumenter du code pour analyser la latence tout au long du cycle de vie d'un appel ou d'une requête utilisateur. Les traces fournissent une vue d'ensemble de la latence que chaque composant contribue à la latence totale dans un système. Les traces peuvent s'étendre sur plusieurs processus Go.
  • Debugging : Le debugging nous permet de mettre en pause un programme Go et d'examiner son exécution. L'état et le flux du programme peuvent être vérifiés avec le debugging.
  • Statistiques et événements du runtime : La collecte et l'analyse des statistiques et événements du runtime fournissent une vue d'ensemble de l'état de santé des programmes Go. Les pics et creux de métriques nous aident à identifier les changements de débit, d'utilisation et de performance.

Remarque : Certains outils de diagnostics peuvent interférer les uns avec les autres. Par exemple, le profiling mémoire précis fausse les profils CPU, et le profiling de blocage de goroutine affecte la trace du scheduler. Utilise les outils isolément pour obtenir des informations plus précises.

Profiling

Le profiling est utile pour identifier les sections de code coûteuses ou fréquemment appelées. Le runtime Go fournit des données de profiling dans le format attendu par l' outil de visualisation pprof. Les données de profiling peuvent être collectées pendant les tests via go test ou via des endpoints rendus disponibles par le package net/http/pprof. Les utilisateurs doivent collecter les données de profiling et utiliser les outils pprof pour filtrer et visualiser les chemins de code les plus importants.

Profils prédéfinis fournis par le package runtime/pprof :

  • cpu : Le profil CPU détermine où un programme passe son temps en consommant activement des cycles CPU (par opposition au temps passé à dormir ou à attendre des E/S).
  • heap : Le profil heap rapporte les échantillons d'allocation mémoire ; utilisé pour surveiller l'utilisation mémoire courante et historique, et pour détecter les fuites mémoire.
  • threadcreate : Le profil de création de threads rapporte les sections du programme qui mènent à la création de nouveaux threads OS.
  • goroutine : Le profil goroutine rapporte les stack traces de toutes les goroutines courantes.
  • block : Le profil block montre où les goroutines se bloquent en attendant sur des primitives de synchronisation (y compris les timer channels). Le profil block n'est pas activé par défaut ; utilise runtime.SetBlockProfileRate pour l'activer.
  • mutex : Le profil mutex rapporte les contentions de verrous. Quand tu penses que ton CPU n'est pas pleinement utilisé à cause d'une contention de mutex, utilise ce profil. Le profil mutex n'est pas activé par défaut, voir runtime.SetMutexProfileFraction pour l'activer.

Quels autres profilers puis-je utiliser pour profiler des programmes Go ?

Sur Linux, les outils perf peuvent être utilisés pour profiler des programmes Go. Perf peut profiler et dérouler le code cgo/SWIG et le noyau, il peut donc être utile pour obtenir des informations sur les goulots d'étranglement de performance natifs/noyau. Sur macOS, la suite Instruments peut être utilisée pour profiler des programmes Go.

Puis-je profiler mes services en production ?

Oui. Il est sûr de profiler des programmes en production, mais activer certains profils (par exemple, le profil CPU) ajoute un coût. Tu dois t'attendre à observer une dégradation des performances. La pénalité de performance peut être estimée en mesurant la surcharge du profiler avant de l'activer en production.

Tu peux vouloir profiler périodiquement tes services en production. En particulier dans un système avec plusieurs répliques d'un seul processus, sélectionner une réplique aléatoire périodiquement est une option sûre. Sélectionne un processus de production, profile-le pendant X secondes toutes les Y secondes et sauvegarde les résultats pour la visualisation et l'analyse ; puis recommence périodiquement. Les résultats peuvent être revus manuellement et/ou automatiquement pour trouver des problèmes. La collecte de profils peut interférer les uns avec les autres, il est donc recommandé de ne collecter qu'un seul profil à la fois.

Suis-je limité aux profils intégrés ?

En plus de ce que fournit le runtime, les utilisateurs Go peuvent créer leurs profils personnalisés via pprof.Profile et utiliser les outils existants pour les examiner.

Puis-je servir les handlers du profiler (/debug/pprof/...) sur un chemin et un port différents ?

Oui. Le package net/http/pprof enregistre ses handlers sur le mux par défaut, mais tu peux aussi les enregistrer toi-même en utilisant les handlers exportés depuis le package.

Par exemple, l'exemple suivant servira le handler pprof.Profile sur :7777 à /custom_debug_path/profile : 

package main

import (
	"log"
	"net/http"
	"net/http/pprof"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/custom_debug_path/profile", pprof.Profile)
	log.Fatal(http.ListenAndServe(":7777", mux))
}

Tracing

Le tracing est un moyen d'instrumenter du code pour analyser la latence tout au long du cycle de vie d'une chaîne d'appels. Go fournit le package golang.org/x/net/trace comme backend de tracing minimal par nœud Go et fournit une bibliothèque d'instrumentation minimale avec un tableau de bord simple. Go fournit également un execution tracer pour tracer les événements du runtime dans un intervalle de temps.

Le tracing nous permet de :

  • Instrumenter et analyser la latence des applications dans un processus Go.
  • Mesurer le coût d'appels spécifiques dans une longue chaîne d'appels.
  • Déterminer les améliorations d'utilisation et de performance. Les goulots d'étranglement ne sont pas toujours évidents sans données de tracing.

Dans les systèmes monolithiques, il est relativement facile de collecter des données de diagnostics depuis les blocs constitutifs d'un programme. Tous les modules vivent dans un processus et partagent des ressources communes pour rapporter les logs, les erreurs et d'autres informations de diagnostics. Une fois que ton système dépasse un seul processus et commence à devenir distribué, il devient plus difficile de suivre un appel depuis le serveur web front-end vers tous ses back-ends jusqu'à ce qu'une réponse soit renvoyée à l'utilisateur. C'est là que le tracing distribué joue un rôle important pour instrumenter et analyser tes systèmes en production.

Le tracing distribué est un moyen d'instrumenter du code pour analyser la latence tout au long du cycle de vie d'une requête utilisateur. Quand un système est distribué et quand les outils de profiling et de debugging conventionnels ne passent pas à l'échelle, tu peux utiliser des outils de tracing distribué pour analyser les performances de tes requêtes utilisateur et RPC.

Le tracing distribué nous permet de :

  • Instrumenter et profiler la latence des applications dans un grand système.
  • Tracer tous les RPCs dans le cycle de vie d'une requête utilisateur et voir les problèmes d'intégration qui ne sont visibles qu'en production.
  • Déterminer les améliorations de performance applicables à nos systèmes. De nombreux goulots d'étranglement ne sont pas évidents avant la collecte de données de tracing.

L'écosystème Go fournit diverses bibliothèques de tracing distribué par système de tracing et des bibliothèques indépendantes du backend.

Existe-t-il un moyen d'intercepter automatiquement chaque appel de fonction et de créer des traces ?

Go ne fournit pas de moyen d'intercepter automatiquement chaque appel de fonction et de créer des spans de trace. Tu dois instrumenter manuellement ton code pour créer, terminer et annoter les spans.

Comment propager les en-têtes de trace dans les bibliothèques Go ?

Tu peux propager les identifiants de trace et les tags dans le context.Context. Il n'existe pas encore de clé de trace canonique ni de représentation commune des en-têtes de trace dans l'industrie. Chaque fournisseur de tracing est responsable de fournir des utilitaires de propagation dans ses bibliothèques Go.

Quels autres événements de bas niveau de la bibliothèque standard ou du runtime peuvent être inclus dans une trace ?

La bibliothèque standard et le runtime essaient d'exposer plusieurs APIs supplémentaires pour notifier sur des événements internes de bas niveau. Par exemple, httptrace.ClientTrace fournit des APIs pour suivre les événements de bas niveau dans le cycle de vie d'une requête sortante. Un effort continu est en cours pour récupérer les événements de bas niveau du runtime depuis l'execution tracer du runtime et permettre aux utilisateurs de définir et d'enregistrer leurs événements utilisateur.

Debugging

Le debugging est le processus d'identification de la raison pour laquelle un programme se comporte mal. Les debuggers nous permettent de comprendre le flux d'exécution et l'état courant d'un programme. Il existe plusieurs styles de debugging ; cette section se concentrera uniquement sur l'attachement d'un debugger à un programme et le debugging de core dump.

Les utilisateurs Go utilisent principalement les debuggers suivants :

  • Delve : Delve est un debugger pour le langage de programmation Go. Il prend en charge les concepts du runtime de Go et les types intégrés. Delve essaie d'être un debugger fiable et complet pour les programmes Go.
  • GDB : Go fournit le support GDB via le compiler Go standard et Gccgo. La gestion de la pile, le threading et le runtime contiennent des aspects qui diffèrent suffisamment du modèle d'exécution attendu par GDB pour qu'ils puissent dérouter le debugger, même quand le programme est compilé avec gccgo. Même si GDB peut être utilisé pour déboguer des programmes Go, ce n'est pas idéal et peut créer de la confusion.

Dans quelle mesure les debuggers fonctionnent-ils avec les programmes Go ?

Le compiler gc effectue des optimisations telles que l'inlining de fonctions et la registerisation de variables. Ces optimisations rendent parfois le debugging avec des debuggers plus difficile. Un effort continu est en cours pour améliorer la qualité des informations DWARF générées pour les binaires optimisés. Jusqu'à ce que ces améliorations soient disponibles, nous recommandons de désactiver les optimisations lors de la construction du code en cours de débogage. La commande suivante construit un package sans optimisations du compiler : 

$ go build -gcflags=all="-N -l"

Dans le cadre de l'effort d'amélioration, Go 1.10 a introduit un nouveau flag du compiler -dwarflocationlists. Ce flag incite le compiler à ajouter des listes de localisation qui aident les debuggers à travailler avec les binaires optimisés. La commande suivante construit un package avec des optimisations mais avec les listes de localisation DWARF : 

$ go build -gcflags="-dwarflocationlists=true"

Quelle est l'interface utilisateur de debugger recommandée ?

Même si delve et gdb fournissent tous deux des CLIs, la plupart des intégrations d'éditeurs et des IDEs fournissent des interfaces utilisateur spécifiques au debugging.

Est-il possible de faire du debugging post-mortem avec des programmes Go ?

Un fichier core dump est un fichier qui contient le dump mémoire d'un processus en cours d'exécution et son état de processus. Il est principalement utilisé pour le debugging post-mortem d'un programme et pour comprendre son état pendant qu'il est encore en cours d'exécution. Ces deux cas font du debugging de core dumps un bon outil de diagnostic pour l'analyse post-mortem des services en production. Il est possible d'obtenir des fichiers core depuis des programmes Go et d'utiliser delve ou gdb pour déboguer, voir la page core dump debugging pour un guide pas à pas.

Statistiques et événements du runtime

Le runtime fournit des statistiques et des rapports d'événements internes pour les utilisateurs afin de diagnostiquer les problèmes de performance et d'utilisation au niveau du runtime.

Les utilisateurs peuvent surveiller ces statistiques pour mieux comprendre l'état de santé général et les performances des programmes Go. Quelques statistiques et états fréquemment surveillés :

  • runtime.ReadMemStats rapporte les métriques liées à l'allocation heap et au garbage collection. Les statistiques mémoire sont utiles pour surveiller la quantité de ressources mémoire qu'un processus consomme, si le processus peut bien utiliser la mémoire, et pour détecter les fuites mémoire.
  • debug.ReadGCStats lit les statistiques sur le garbage collection. Il est utile de voir quelle proportion des ressources est dépensée sur les pauses GC. Il rapporte également une chronologie des pauses du garbage collector et les percentiles de durée de pause.
  • debug.Stack retourne la stack trace courante. La stack trace est utile pour voir combien de goroutines sont en cours d'exécution, ce qu'elles font, et si elles sont bloquées ou non.
  • debug.WriteHeapDump suspend l'exécution de toutes les goroutines et te permet de dumper le heap vers un fichier. Un heap dump est un instantané de la mémoire d'un processus Go à un moment donné. Il contient tous les objets alloués ainsi que les goroutines, les finaliseurs, et plus encore.
  • runtime.NumGoroutine retourne le nombre de goroutines courantes. La valeur peut être surveillée pour voir si suffisamment de goroutines sont utilisées, ou pour détecter des fuites de goroutines.

Execution tracer

Go est livré avec un execution tracer du runtime pour capturer un large éventail d'événements du runtime. La planification, les syscalls, le garbage collection, la taille du heap et d'autres événements sont collectés par le runtime et disponibles pour visualisation avec go tool trace. L'execution tracer est un outil pour détecter les problèmes de latence et d'utilisation. Tu peux examiner dans quelle mesure le CPU est utilisé, et quand le réseau ou les syscalls sont à l'origine de la préemption des goroutines.

Le tracer est utile pour :

  • Comprendre comment tes goroutines s'exécutent.
  • Comprendre certains des événements clés du runtime, tels que les exécutions du GC.
  • Identifier les exécutions mal parallélisées.

Cependant, il n'est pas idéal pour identifier les points chauds tels que l'analyse de la cause d'une utilisation excessive de la mémoire ou du CPU. Utilise plutôt les outils de profiling en premier pour les résoudre.

GODEBUG

Le runtime émet également des événements et des informations si la variable d'environnement GODEBUG est définie en conséquence.

  • GODEBUG=gctrace=1 affiche les événements du garbage collector à chaque collecte, en résumant la quantité de mémoire collectée et la durée de la pause.
  • GODEBUG=inittrace=1 affiche un résumé du temps d'exécution et des informations d'allocation mémoire pour le travail d'initialisation de package terminé.
  • GODEBUG=schedtrace=X affiche les événements de scheduling toutes les X millisecondes.

La variable d'environnement GODEBUG peut être utilisée pour désactiver l'utilisation des extensions d'ensemble d'instructions dans la bibliothèque standard et le runtime.

  • GODEBUG=cpu.all=off désactive l'utilisation de toutes les extensions d'ensemble d'instructions optionnelles.
  • GODEBUG=cpu.extension=off désactive l'utilisation des instructions de l' extension d'ensemble d'instructions spécifiée.
    extension est le nom en minuscules de l'extension d'ensemble d'instructions, tel que sse41 ou avx.
